# Infooo Prep

Infooo Prep is a full-stack learning platform for Romanian high-school students preparing for the Computer Science Baccalaureate exam. It combines structured C++ lessons and practice problems with an in-browser code runner backed by Judge0.

The project is currently under active development. The end-to-end **Run code** flow is working: the Next.js client sends C++ source code and standard input to FastAPI, Judge0 compiles and executes it in an isolated environment, and the result is displayed in the browser. The backend can also evaluate a solution against a problem's test cases and persist the verdict.

## Tech stack

- **Frontend:** Next.js 16, React 19, TypeScript, Tailwind CSS 4
- **Backend:** Python 3.11, FastAPI, Pydantic, SQLAlchemy
- **Data:** PostgreSQL 16
- **Code execution:** Judge0 1.13.1, Redis, GCC / C++17
- **Infrastructure:** Docker, Docker Compose
- **Testing:** pytest, FastAPI TestClient

## Architecture

```text
Next.js client (localhost:3000)
          |
          | HTTP / JSON
          v
FastAPI API (localhost:8000) --------> Application PostgreSQL
          |
          | synchronous submission
          v
Judge0 API (localhost:2358) ---------> Judge0 PostgreSQL
          |
          v
       Redis queue
          |
          v
Judge0 worker / isolated C++ execution
```

The application database stores users, chapters, lessons, problems, test cases and submission history. Judge0 uses its own PostgreSQL database and Redis queue; application data and execution-engine data are deliberately kept separate.

For a judged submission, the backend loads the problem's tests, executes the submitted program once per test, compares normalized output and stops at the first failure. The final verdict and test count are saved in `user_submissions`.

## Main features

- Responsive learning interface with chapters, lessons and problem pages
- Editable C++ workspace with custom standard input
- Sandboxed compilation and execution through a self-hosted Judge0 instance
- Clear output for successful runs, compilation errors and runtime errors
- Automated solution checking against visible and hidden test cases
- Verdicts for accepted, wrong answer, compilation error, runtime error and time limit exceeded
- Relational data model for learning content and submission history
- Interactive OpenAPI documentation generated by FastAPI

## Run locally

### Prerequisites

- Docker Desktop with Docker Compose
- Node.js 20 or newer
- npm

Judge0 runs privileged containers, so the complete stack requires a local Docker environment that supports privileged mode.

### 1. Configure the services

Create a root `.env` file for the application database:

```dotenv
APP_DB_NAME=infooo_prep
APP_DB_USER=infooo_user
APP_DB_PASSWORD=choose-a-local-password
```

Create the private Judge0 configuration from the committed example:

```bash
cp judge0/judge0.conf.example judge0/judge0.conf
```

Replace the placeholder Redis password, PostgreSQL password and secret key in `judge0/judge0.conf`. Both configuration files are ignored by Git.

Create `frontend/.env.local`:

```dotenv
NEXT_PUBLIC_API_URL=http://localhost:8000
```

### 2. Start the backend and execution services

From the repository root:

```bash
docker compose up --build
```

In a second terminal, add the current demo content to the application database:

```bash
docker compose exec api python -m app.seed
```

The seed operation is idempotent and currently creates two local users, one chapter, three lessons, two problems and their test cases. The local passwords in the seed data are placeholders; authentication is not implemented yet.

### 3. Start the frontend

```bash
cd frontend
npm install
npm run dev
```

Open:

- Web application: [http://localhost:3000](http://localhost:3000)
- API documentation: [http://localhost:8000/docs](http://localhost:8000/docs)
- Judge0 API: [http://localhost:2358](http://localhost:2358)

## API overview

| Method | Endpoint | Purpose |
| --- | --- | --- |
| `GET` | `/chapters/` | List chapters |
| `GET` | `/chapters/{chapter_id}` | Get one chapter |
| `GET` | `/chapters/{chapter_id}/lessons` | List a chapter's lessons |
| `GET` | `/chapters/{chapter_id}/problems` | List a chapter's problems |
| `GET` | `/lessons/{lesson_id}` | Get one lesson |
| `GET` | `/problems/` | List problems |
| `GET` | `/problems/{problem_id}` | Get one problem |
| `POST` | `/submission/run` | Compile and run C++ with custom input |
| `POST` | `/submission/problems/{problem_id}/submit` | Evaluate and persist a solution |

Example run request:

```bash
curl -X POST http://localhost:8000/submission/run \
  -H "Content-Type: application/json" \
  -d '{"source_code":"#include <iostream>\nint main(){std::cout << 42;}","stdin":""}'
```

## Tests and checks

Start the complete Docker stack first, then start the isolated test database:

```bash
docker compose --profile test up -d test_database
```

Run the backend suite from the project root:

```bash
pytest
```

The current suite contains 20 tests covering chapter, lesson and problem endpoints, validation and not-found cases, verdict calculation, submission persistence, and real Judge0 scenarios for accepted code, compilation errors and runtime errors. Tests refuse to run unless the configured database name ends in `_test`.

Frontend checks:

```bash
cd frontend
npm run lint
npm run build
```

## Design decisions and trade-offs

- **Self-hosted execution:** Judge0 provides isolated code execution without placing compiler processes inside the API container. This makes the local setup heavier, but keeps execution concerns outside the application backend.
- **Separate databases:** Judge0 internals and platform data have different ownership and schemas, so each uses its own PostgreSQL service.
- **Synchronous judging:** the API currently waits for Judge0 after each test. This keeps the first implementation easy to follow, but longer submissions should eventually move to an asynchronous job flow.
- **Static frontend content:** local TypeScript fixtures made it possible to develop the learning experience before the content API was complete. Replacing them with backend queries is the next integration step.
- **Schema creation on startup:** SQLAlchemy currently creates tables when FastAPI starts. A migration tool such as Alembic is needed before production use.
